# Plan: hash-pinned dependency locks (issue #218)

## Context

The `requirements-*.txt` layers used `>=` floors, so every image build, CI run and Pi install
resolved whatever was newest that day. Two builds of the same commit could ship different
packages, nothing verified what was downloaded, and a CVE in a transitive dependency surfaced only
if someone went looking. #278's `_DEPS_EPOCH` capped how stale a cached pip layer could get (one
week), which also meant versions moved silently once a week.

Goal: every install takes exact, sha256-verified versions; versions move only through a reviewed
PR; a known vulnerability is loud. Keep the layering (base / ml / report / dev) and prod-rollout's
base-only test run.

## Design

- **Inputs stay the `.txt` files** (floors, comments, human-edited). **`scripts/lock_deps.sh`**
  compiles them with `uv pip compile --generate-hashes` into:

  | Lock | From | Target | Installed by |
  |---|---|---|---|
  | `requirements-base.lock` | `requirements-base.txt` | CPython 3.12, x86_64 manylinux | `Dockerfile.mcp`/`.report`, `lean-import`, prod-rollout |
  | `requirements-ml.lock` | `requirements-ml.txt`, `-c` base lock | same | `Dockerfile.api`/`.news` |
  | `requirements-dev.lock` | `requirements-dev.txt`, `-c` base lock | same | `deploy.yml` `gate` |
  | `keyproxy/requirements.lock` | `keyproxy/requirements.txt` | same | `Dockerfile.keyproxy` |
  | `requirements.lock` | `requirements.txt` | `--universal`, python >= 3.11 | local dev, the Pi |

  Modes: plain (re-lock, keeping pins that still satisfy the inputs), `--upgrade`, `--check`.
- **Every install is `pip install --require-hashes -r <lock>`.** The Dockerfiles `COPY` only the
  lock before installing, so the pip layer's cache key is the lock: it rebuilds exactly when the
  lock changes. `_DEPS_EPOCH` and the `pip install --upgrade pip` lines are gone.
- **CI:** the `gate` job installs the dev lock and runs `lock_deps.sh --check` (a `.txt` edited
  without re-locking fails). A new `dep-audit` job runs `scripts/audit_deps.sh` (pip-audit over all
  five locks).
- **Updates:** `.github/workflows/deps-lock-update.yml` runs Mondays 09:17 UTC and on dispatch:
  `lock_deps.sh --upgrade`, audit, and if any lock changed, force-push `deps/lock-update` and
  open/refresh one PR against main. The workflow goes red if the audit failed.
- **Guard:** `tests/test_dependency_locks.py` (static): every pin hashed, locks generated by the
  script, ml/dev agree with base, base stays lean, torch is the `+cpu` build, each Dockerfile
  installs its lock with `--require-hashes`, CI and prod-rollout wiring, no `DEPS_EPOCH`, the
  update workflow relocks/audits/opens a PR.

## Gotchas (record of what would mislead)

1. **The PyTorch CPU index shadows numpy.** `download.pytorch.org/whl/cpu` mirrors numpy, and
   others. uv's default index strategy takes a package only from the first index that has it, so it
   locked numpy at whatever old version that mirror carried. `--index-strategy unsafe-best-match`
   is what pip does (best version across indexes). `--emit-index-url` writes the extra index into
   the lock so `pip install -r` can find `torch==…+cpu`.
2. **Platform targeting.** Without `--python-platform x86_64-manylinux_2_28 --python-version 3.12`
   uv resolves for the Mac running it (Python 3.14 locally), and the hashes would be for the wrong
   wheels. The universal lock is the only one meant for non-container machines.
3. **`--check` must compile in a scratch copy holding the committed locks.** Compiling from scratch
   with no prior lock picks up any upstream release and fails the check for reasons unrelated to
   the PR. The copy keeps the same relative paths, so the `# via` annotations (which name the input
   files) still match byte for byte.
4. **A relative `uv` path breaks after `cd` into the scratch dir.** The script resolves it to an
   absolute path first.
5. **pip-audit's default PyPI service skips `torch 2.x+cpu`** ("not found on PyPI") with exit 0, so
   the biggest package went unaudited. `--vulnerability-service osv` covers it. With OSV,
   `--require-hashes` only checks that hashes are *present*. The real verification is pip's at
   install time. Negative test: a `requests==2.19.0` pin was reported with 10 advisories, exit 1.
6. **`dep-audit` is deliberately not in `deploy`'s `needs`.** A new advisory against an unchanged
   lock would otherwise block every unrelated merge from reaching test. It goes red; the fix is a
   floor bump or `lock_deps.sh --upgrade`.
7. **PRs opened with `GITHUB_TOKEN` don't trigger workflows,** so the weekly PR would have no CI
   and couldn't pass the required checks. Also, the org/repo setting "Allow GitHub Actions to create
   and approve pull requests" must be on for `gh pr create` to work at all. Choice (John's): turn
   that setting on and re-run CI on the PR by hand, **or** add a fine-grained PAT as the
   `DEPS_PR_TOKEN` secret (contents + pull-requests write), which the workflow prefers when set.
   Dependabot was ruled out: it doesn't update uv-compiled hashed requirements
   (dependabot-core#10478).
8. **My own Dockerfile comment tripped the "no `--upgrade pip`" test.** The assertion is now a
   regex on `RUN` lines only.
9. **The Pi needs a 64-bit OS.** PyTorch publishes aarch64 manylinux wheels but none for 32-bit
   armv7, so `pip install --require-hashes -r requirements.lock` fails on 32-bit Pi OS.
10. **Not covered:**
    - pip doesn't hash-check the *build* dependencies of a package that installs from an sdist.
      Every package in the container locks currently resolves to a wheel.
    - The `python:3.12-slim` base image is still a floating tag.
